Found so far with the harness (2026-10-10): the IU runs the PROM in boot
mode from the first cycle; uncached fetches cost ~8 cycles each (IE off:
the suite runs with the caches off except in the MMU tests), so the whole
suite needs hundreds of millions of cycles (~5 min of Verilator). Fixed on
the way: two harness bugs (a phantom beat after each ack; the I/O-bus
bridge gave the ESCC a word address — it decodes addr[2:1]); the walker
dropped its memory request after one cycle, so the arbiter released the
port and the ack reached nobody (the first MMU-on fetch hung); the suite's
`mmu_off` clears tags with word stores to ASI 0x0C/0x0E, which the data
side only took as doublewords (now a word writes its half, the other half
0); the walk's owner was not held through the done cycle (a faulting walk
looped forever); a read of the SFSR returned the cleared value (the
register read data is now captured at the ack edge); the walker's R/M
write-back left a stale PTE line in the D-cache (the module invalidates
the line itself: the D-cache ignores its own module's snoops).
Then: an atomic to an empty slot left the arbiter locked for a write that
never came (every later fetch hung); the instruction side's bus errors
were not reported to the SFSR (0x874); a plain store's bus error must not
trap (posted: the chipset's AFSR); after a faulting fetch the IU issued
the next fetch, whose fault set SFSR.OW (Solaris loops on OW) — the IU now
holds fetches until the trap flushes. Progression of the runs: 33 → 36 →
58/5 → 62/1 → 63/2 → **65/0**. The same binary with `+gaps +lat=4`
(memory latency 4, a bubble between burst beats): **65/0** as well.

**Speed (2026-10-10):** the fetch and load paths were reworked so that a
cache hit answers in the cycle after the request: the sides translate in
the cycle the IU asks (the TLB lookup is combinational on flops), the
cache indexes its RAMs from the VA (`idx_i`) and answers from its compare
cycle, taking the next request in that same cycle, and the sides' answers
to the IU are combinational from the cache's done. On hits the IU fetches
one instruction per cycle; uncached accesses take ~6 cycles in the
harness (the memory model's latency). Found on the way: the store byte
enables must come from the PA of the request cycle, not the latched one

**The shim (new repo, `rtl/hybrid/`, copied verbatim to the old repo's

- `plomb_master.sv`: `mem_pkg` → PLOMB master. **Every beat is a single**
  (burst code 00): a doubleword is two word beats (high word first), a
  32-byte line eight; PLOMB bursts were not used because their beat/`cont`
  protocol is not described by the package and the slaves' implementation
  is off limits — a later optimisation, to be validated on the board.
  Writes use `WR_ACK` (mode 11) so every beat gets a response; the
  request is latched at acceptance; a lone word is returned in both
  halves; after an error ack the remaining responses of a line are drained
  silently; own acknowledged write beats are announced as snoops (MID 8;
  the I-cache invalidates on its own stores). `be[3]` is the byte at a+0
  (`d[31:24]`), which the VHDL side maps to `be(0)` by position. `dack`
  is always high. ASI field 0x20, `cache` = `cacheable_pa`, `lock`
  mirrored from the request.
- `cpu_plomb.sv`: `cpu_module` + `plomb_master`, flat ports; DMA write
  snoops (the I/O master's accepted write beats, MID 0) queued behind the
  module's own, consecutive beats of one line folded.
- Old repo `rtl/hybrid/cpu_hyb.vhd`: the records ↔ flat ports;
  `rst = preset OR NOT reset_n`; `errmode` **stays low**: the module's
  watchdog is internal (IU reset, BM, SFSR.EM), while the old top's
  `wdreq` path would do a system reset through the software-reset path and
  wipe the module (SFSR.EM included). Consequence: a watchdog reset in the
  hybrid does not reset the devices and does not set the old top's WD

### The whole-machine simulation finds the shim's three faults (2026-10-10, 12:30-13:15)

The old repo has a whole-machine Verilator flow (`sim/README.md`): GHDL 6
lowers `ss_core` to one Verilog file (`sim/gen_verilog.sh 20`),
`sim/build.sh 20` verilates it with the harness (`sim_main.cpp`: DDR, the
ROM download, SD, ttya decoded from the `uart_txd` pin), `sim/run-cputest.sh
20` runs the CPU suite as the boot PROM. It now takes the hybrid:
`build.sh` adds the `rtl/new` and `rtl/hybrid` SystemVerilog (GHDL leaves
`cpu_plomb`, `m48t08_pvc`, … as black-box instances with their generics);
`gen_verilog.sh` no longer needs bash 4; `ts_inter.vhd` got a static port
actual (GHDL refuses a concatenation there); the old `fpu` entities are not
generated with `HYBCPU0` (name clash with the new module). GHDL 6.0.0 for
Apple Silicon is unpacked in the session scratch (`ghdl-llvm-6.0.0-macos15-
aarch64`, from the GitHub release; Homebrew's 5.1.1 snapshot refuses
`acia.vhd` with "non matching bounds"); misterubuntu has only GHDL 4.1.
Speed: ~650 kHz; the test ROM's banner comes after ~11 M bus cycles (the
ROM copies itself to RAM first; boot-mode fetches are uncached and the CPU
runs at half rate), the suite needs ~1.5 G.

Traces (`--trace F.vcd --trace-from N`, `sim/vcd.py F.vcd list|show REGEX`;
the hybrid's signals keep their names: `…i_ts_core.dosmp_ihyb0_i_cpu_hyb0.
{ph,cpu_edge,pb_*,u.u_cpu.*,u.u_pb.*}`, `…i_ts_io.i_ts_sport2.u.*` is the
serial ESCC's shim) showed, one after the other:
1. **The CPU never saw an ack.** Its clock is a toggle flop, so its edge
   comes after the bus edge it belongs to (the flop and the clock network;
   in Verilator the derived clock's processes run after the bus domain's
   updates, which models the same thing); the shim showed each ack only
   until that bus edge, so the CPU sampled the cleared registers and
   refetched the reset vector forever. Fix: everything the CPU sees is a
   register loaded when `cpu_ld_i` is high (the bus cycle ending on the
   edge between two CPU edges, `= ph`) and held for a CPU cycle; a request
   finishes once the final ack is being shown in a cycle ending on a CPU
   edge (`cpu_edge_i = NOT ph`), so S_IDLE first looks at the CPU's
   outputs after it has moved on (leaving earlier re-accepted the request
   the CPU was dropping and issued it twice — a duplicate error response
   then hit the next access, a spurious tt 0x21 in `t_buserr`). The
   `sim/cpu` bench had hidden this with an ideal half-rate waveform; it
   uses the flop-derived clock again (`+half`, `-GHALF=1`).
